# Independent security and data-integrity review

Reviewed the current `src/notes.ts`, `src/note-format.ts`, `src/main.ts`, `src/settings.ts`, and `src/source.ts`, plus their callers in `src/view.ts`. No implementation or test files were changed. Findings below are ordered by impact; line numbers refer to the reviewed files.

## Findings

### P1 — Provider text can enter a note as a Templater command

`src/source.ts:108` retains article date text, and `src/source.ts:190-212` accepts Steam `price.formatted` as an arbitrary string. `src/note-format.ts:59,63` interpolates both directly into Markdown. A provider response containing `<%* tp.file.rename("owned") %>` in an article `<time>` reaches the saved note unchanged when the articles group is selected. A similarly crafted Steam price does the same when the Steam group is selected. If Templater processes the newly created note, source-controlled text crosses into executable template syntax. **Smallest fix:** escape active template/HTML openers in these two rendered values using the same boundary treatment already applied to descriptions and link labels; test the full parse-to-note path for both fields.

### P1 — Changing property mappings strands existing notes and enables duplicates

`src/settings.ts:43-46` accepts a new valid mapping without retaining the mapping used by each existing note. `src/note-format.ts:103-109` reads only the current mapped `game_id`; `src/main.ts:76` then rebuilds the index. Changing `game_id` to `catalog_id` makes an existing note with `game_id: gnd:x` disappear from the library. `src/notes.ts:39-42,111-126` can then create a second note for that game. Changing personal mappings similarly makes existing values appear missing. **Fix under implementation:** retain a per-note schema snapshot in plugin data so new mappings apply to future notes while existing reads, writes, and refreshes use their original names; verify repeat add and refresh across a mapping change. This avoids automatic mass migration.

### P2 — Logging a session discards YAML comments and formatting

`src/notes.ts:154-166` parses the entire frontmatter into a plain object, updates playtime, and serializes the whole object back. YAML comments are not represented in that object, so a user-authored comment in an otherwise valid game note is removed on the first session log. The saved body is carried forward, but the frontmatter is not preserved verbatim. **Smallest fix:** use a frontmatter update operation that edits the one playtime property while preserving unrelated source text, or explicitly preserve and restore comments with a tested parser. Verify a note with comments and a session entry in real Obsidian.

### P2 — Renaming a newly created note bypasses duplicate detection until reload

`src/notes.ts:127` caches the created path by game ID. `src/main.ts:53` updates the library index on rename but never updates that cache. `src/notes.ts:40-42` prefers the stale cached path and does not fall back to the index when it no longer resolves. During the same plugin session, adding the same game after moving or renaming its note can create a duplicate. **Smallest fix:** remove the stale cache entry on rename or fall back to the indexed match when the cached path is absent. Test create → rename → repeat add.

### P2 — The current tree is not ready for official directory submission

The root has no `README.md`. Obsidian's [submission guide](https://docs.obsidian.md/Plugins/Releasing/Submit%20your%20plugin) lists it as a prerequisite, and the [developer policies](https://docs.obsidian.md/community-directory/developer-policies) require network use and remote services to be clearly disclosed there. The code contacts Games Never Die, its media host, and may load remote cover images (`src/main.ts:26-35`, `src/view.ts:86-99`). **Smallest fix:** add a README that explains the user-initiated network mode, destinations and purpose before submission. This review's file restriction leaves that work to the implementation owner.

## Verification and limits

- `npm test -- --reporter=dot`: 28 tests passed in two files. Existing tests do not cover the failures above.
- A local, read-only Node/esbuild experiment confirmed that changing the mapped ID makes `libraryItem` return `null` for an existing note.
- A local, read-only jsdom experiment modified the repository's game HTML fixture in memory: `parseGame` returned the hostile article date, and `sourceBody` emitted the raw Templater opener. A pure rendering check also found the raw opener in Steam price output.
- Rename handling and YAML comment loss follow directly from the cited control flow. They were not exercised in a live vault; this review did not change the shared test vault or any network service.

## Correction

The earlier P1 claim that the Settings network switch could not disable access was wrong. Re-reading `src/settings.ts:19` shows its control key is `online`, matching the setting read by the request guards. The earlier `parseSettings({network:false})` experiment used a key that the UI does not send and did not test the actual binding. That finding and its purported verification have been withdrawn.
